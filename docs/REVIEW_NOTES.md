# ملاحظات المراجعة — NexusCore

> **الحالة:** ملاحظات للمراجعة. **لم يُنفَّذ أي تعديل** على الكود بسببها.
> كل ملاحظة عليها وسم يوضح درجة التأكد:
> - ✅ **مؤكَّدة بالتشغيل**: أعدتُ إنتاجها بتجربة فعلية على PostgreSQL.
> - 👁 **من قراءة الكود**: واضحة في الكود لكنها لم تُجرَّب بالتشغيل.
>
> الدرجات: 🔴 عالية (بيانات مالية / أمان) · 🟠 متوسطة · 🟡 منخفضة / تحسين.
> العمود **القرار** هو ما أحتاج رأيك فيه قبل التنفيذ.

## A) سلامة البيانات المالية 🔴

### A1 — مبالغ غير صالحة تُقبل وتُخزَّن كـ `NaN` أو سالبة ✅ — **✔ نُفِّذ**
> أُضيف `server/validation.ts` وتحقق في: الدفعات (المبلغ والتاريخ والطريقة)، `apply-credit`، إنشاء الفاتورة، وبنود الفواتير وعروض الأسعار. اختبارات: `tests/integration/money-validation.test.ts`.
> **ما زال مطلوباً:** فحص بيانات الإنتاج الحالية بالاستعلامات في آخر الملف.

**الأماكن:** `server/database-routes.ts`
- `POST /api/invoices/:id/payments` (`parseFloat(req.body.amount)` بلا أي تحقق)
- `POST /api/invoices/:invoiceId/apply-credit`
- (نفس الخطأ أُصلح سابقاً في `adjust-balance` لمصادر الدفع)

**ما حدث في التجربة:**
| الطلب | النتيجة |
|---|---|
| دفعة `amount: "abc"` | `201`، وصارت `paidAmount = "NaN"` للفاتورة |
| دفعة `amount: -40` | `201`، وصارت `paidAmount = "-40.00"` |
| دفعة `amount: 0` | `201` |
| `apply-credit` بـ `"abc"` | `200`، وصار رصيد العميل `NaN` |
| `apply-credit` بـ `-50` | `200`، `paidAmount = -50`، والرصيد **زاد** إلى 150 من 100 |

**الأثر:** فساد دائم لبيانات الفاتورة والعميل (`NaN` يبقى في العمود)، وإمكانية توليد رصيد من لا شيء بمبلغ سالب.
**المقترح:** تحقق مركزي (`Number.isFinite(amount) && amount > 0`) يرد 400، ويُطبَّق على الدفعات والاستردادات والرصيد والبنود. يفضَّل استخدام zod schema للمدخلات المالية.
**الجهد:** صغير · **مخاطر تغيير السلوك:** منخفضة (ترفض فقط المدخلات الفاسدة).
**ملاحظة:** يلزم **فحص قاعدة الإنتاج الحالية** بحثاً عن قيم `NaN` أو سالبة موجودة (استعلام SQL مقترح في آخر الملف).

### A2 — حذف العميل مدمِّر وغير ذري ✅
**المكان:** `DELETE /api/clients/:id` (`database-routes.ts`)
- يحذف **الفواتير المدفوعة ودفعاتها وبنودها** وعروض الأسعار وسجل الرصيد بصمت (رسالة النجاح: "Client and all related data deleted successfully").
- العمليات ليست داخل transaction. في التجربة: عميل عليه فاتورة مدفوعة ومصروف مرتبط → الرد `500`، لكن **الفاتورة المدفوعة حُذفت فعلاً** والعميل بقي (حذف جزئي).
- لا يحذف `invoice_history` ولا `client_credentials`... (يعتمد على قيود cascade في السكيما، لم أتحقق منها كلها).

**الأثر:** فقدان سجلات مالية قانونية (فواتير مدفوعة)، وحالات بيانات نصف محذوفة.
**المقترحات (اختر):**
1. منع الحذف إن وُجدت فواتير غير ملغاة أو دفعات (الأسلم)، مع خيار "أرشفة العميل" (`status = inactive`) بدل الحذف.
2. إبقاء الحذف لكن داخل transaction وبمنع الحالات المدفوعة.
3. soft delete للعميل.
**القرار المطلوب:** أي سياسة تريدها للعملاء الذين لديهم فواتير؟

### A3 — Mass assignment في تعديل الفواتير وعروض الأسعار ✅
**المكان:** `PATCH /api/invoices/:id`، `PATCH /api/quotations/:id`
- الفاتورة تُجرَّد من `paidAmount` فقط. في التجربة: `{status:"paid", invoiceNumber:"HACK-1", amount:"1.00"}` → `200` وصارت الفاتورة `paid` بدون أي دفعة، برقم مختلف ومبلغ 1.
- عرض السعر: `{amount:"1", quotationNumber:"X-1"}` → `200`.
- حقول مثل `createdBy` غير الصالحة ترد 500.

**المقترح:** قائمة بيضاء من الحقول القابلة للتعديل (العنوان، الوصف، الملاحظات، الشروط، تاريخ الاستحقاق، نسب الضريبة والخصم)، وأن تمر الحالة والمبالغ عبر مسارات مخصصة فقط (`/payments`, `/cancel`, `/status`, حساب المبلغ من البنود).
**الجهد:** صغير-متوسط · **المخاطر:** قد تعتمد الواجهة على إرسال حقول إضافية؛ يلزم فحص `InvoiceDetail.tsx` و`QuotationDetail.tsx` قبل التنفيذ.

### A4 — تعديل رصيد العميل مباشرة ✅
**المكان:** `PATCH /api/clients/:id` يقبل `creditBalance` و`totalValue`.
- في التجربة: `creditBalance: "99999"` → `200`، ولا يُسجَّل في `client_credit_history`.
- أي مستخدم لديه `crm.edit` يستطيع ذلك (وليس `invoices.approve` كما في بقية عمليات الرصيد).

**المقترح:** إزالة الحقلين من هذا المسار؛ تعديل الرصيد فقط عبر عمليات الرصيد (مع سجل ومن يملك `approve`). `totalValue` يُحسب تلقائياً أصلاً.
**القرار:** هل تحتاج الواجهة تعديل الرصيد يدوياً؟ إن نعم فلتكن "تسوية رصيد" بسبب وسجل.

### A5 — استخدام رصيد عميل لفاتورة عميل آخر ✅
**المكان:** `apply-credit` يأخذ `clientId` من الـ body ولا يقارنه بـ `invoice.clientId`.
- في التجربة: رصيد العميل A طُبِّق على فاتورة العميل B → `200`.

**المقترح:** استخدام `invoice.clientId` دائماً (وتجاهل `clientId` من الطلب أو رفض عدم التطابق).

### A6 — تعديل مبلغ فاتورة مدفوعة ✅
`PATCH` على فاتورة `paid` بضريبة 500 غيّر `amount` إلى 600 وبقيت `status = paid` و`paidAmount = 100` (غير متسق).
**المقترح:** منع تعديل المبالغ بعد وجود دفعات، أو إعادة حساب الحالة (`partially_paid`) تلقائياً.

### A7 — مبالغ فاتورة سالبة ✅ — **✔ نُفِّذ**
`POST /api/invoices` بـ `amount: "-50"` → `201`. (نصّي `"abc"` يرد 500.) يندرج تحت A1.

## B) أخطاء سلوكية 🟠

### B1 — مسارات لا يمكن الوصول إليها (ترتيب التسجيل) ✅
- `GET /api/tasks/performance` معرَّف **بعد** `GET /api/tasks/:id` فيلتقطه الأخير بـ `id="performance"` → `404 Task not found`.
- `GET /api/services/categories` بعد `GET /api/services/:id` → `404 Service not found`.

**المقترح:** نقلهما قبل المسار ذي المعامل. إن كانت الواجهة تستخدمهما فهي معطّلة حالياً بصمت.

### B2 — حذف موظف مرتبط بمستخدم ✅
`DELETE /api/employees/:id` يحاول حذف المستخدم أولاً؛ إن كان قد أنشأ سجلات (عميل، فاتورة…) ينتهك FK ويرد `500` بلا رسالة مفيدة. لا حماية لحذف الموظف الحالي أو آخر أدمن.
**المقترح:** رسالة 409 واضحة، أو تعطيل الحساب بدل حذفه، ومنع حذف الذات/آخر أدمن.

### B3 — 500 بدل 400 في مدخلات غير صالحة ✅
أمثلة مؤكدة: عميل بدون اسم، فاتورة بدون `clientId`، مستخدم بـ `roleId` غير موجود، مهمة بـ `assignedTo` غير موجود، محادثة مع مستخدم غير موجود، فاتورة بمبلغ نصي.
**المقترح:** طبقة تحقق موحدة (zod) + معالج يحوّل أخطاء FK/unique إلى 400/409. (أُصلح جزء منها في المصروفات ومصادر الدفع.)

### B4 — حماية الأدمن ✅
`PUT /api/users/:id/deactivate` يسمح للأدمن بتعطيل نفسه أو آخر أدمن فيُقفل النظام. لا يوجد أيضاً تحقق من وجود `roleId`.

### B5 — مرفقات المصروفات 👁
`ExpenseForm.tsx` يحفظ `attachmentUrl = "/uploads/<اسم الملف>"` لكن لا يوجد رفع فعلي للملف (لا endpoint رفع للمصروفات). الرابط يشير إلى ملف غير موجود. **القرار:** هل الميزة مطلوبة؟ إن نعم أبني endpoint رفع، وإلا تُخفى من الواجهة.

## C) أمان إضافي

### C1 — رفع الملفات 🟠 👁
`database-routes.ts` (multer): الامتداد يؤخذ من `file.originalname` والنوع من `mimetype` الذي يرسله العميل. يمكن رفع ملف `x.html` بـ mimetype `image/png`، وعند تقديمه عبر `res.sendFile` يُقدَّم `text/html` من نفس الأصل (XSS مخزَّن، بشرط أن الضحية مسجَّلة الدخول وتفتح الرابط).
**المقترح:** قائمة بيضاء للامتدادات مطابقة للنوع، وفحص المحتوى (magic bytes)، وترويسة `X-Content-Type-Options: nosniff` و`Content-Disposition: attachment` لغير الصور/PDF.

### C2 — النسخة الاحتياطية 🟠 👁
`GET /api/settings/backup` (أدمن):
- يحتوي **كل رسائل المستخدمين الخاصة** (`messages`) وبيانات العملاء؛ تصدير غير مشفَّر.
- يُحمِّل كل الجداول في الذاكرة ثم `JSON.stringify` (قد ينهار مع بيانات كبيرة).
- لا يتضمن `uploads` ولا `audit_logs` ولا history، ولا يوجد endpoint استعادة، فهو **تصدير وليس نسخة احتياطية قابلة للاستعادة**.
- لا يُسجَّل في سجل التدقيق من نزّله.
**المقترح:** استثناء الرسائل (أو قرار صريح)، تسجيل التنزيل في audit log، والاعتماد على `pg_dump` للنسخ الفعلية.

### C3 — الصلاحيات بالاسم 🟠
- `requireAdmin` يقارن `roleName === 'Admin'` (نصياً). تعديل اسم دور Admin الأساسي يقفل الجميع خارج مسارات الأدمن، وأي دور جديد باسم "Admin" يعتبر أدمن. **المقترح:** علَم `isSystem`/`isAdmin` في جدول الأدوار.
- `credential-routes.ts` يعتبر المستخدم مدير/أدمن إن كان `users.role` (حقل قديم) أو `roleName` يساوي admin/manager. ✅ في التجربة: مستخدم بدور "Sales" لكن `role="manager"` قديم كشف **كلمة مرور** عميل. **المقترح:** الاعتماد على `roleName`/صلاحية صريحة فقط، وتسجيل كل كشف لكلمة مرور في audit log (لا يوجد تسجيل حالياً).

### C4 — كلمات المرور والجلسات 🟠
- الحد الأدنى 8 أحرف دون أي قواعد (✅ `12345678` مقبولة)، و6 أحرف في `/api/register` (معطَّل افتراضياً).
- 👁 تغيير كلمة المرور أو استعادتها لا يُنهي الجلسات الأخرى للمستخدم (لم أجد `session.destroy` في المسارين).
- 👁 لا قفل للحساب (أُضيف تقييد محاولات الدخول سابقاً لكنه في الذاكرة لكل عملية).

### C5 — سجل التدقيق 🟡 👁
`logAudit` في `user-management-routes.ts` يكتب `ipAddress: "127.0.0.1"` و`userAgent: "Development"` ثابتين (بينما `auth.ts` يستخدم IP حقيقياً). حد `limit` في `GET /api/audit-logs` غير محدود الأعلى. السجل لا يغطي الفواتير والدفعات والمصروفات.

- **D1:** `GET /api/tasks` يحمّل **كل** المهام والمستخدمين في الذاكرة ثم يرشّح بـ JS (والـ `limit/offset` بعد ذلك). يحتاج ترشيح وترقيم في SQL.
- **D2:** ملفات ميتة: `server/notification-routes.ts` (غير مسجَّل)، `server/prod.cjs`، `server/simple-prod.js`، `server/replitAuth.ts`، `server/test-email.ts`، `test-api-endpoints.ts`. حذفها بعد موافقتك.
- **D3:** `database-routes.ts` (≈2850 سطراً) يخلط العملاء والفواتير والعروض: يحتاج تقسيماً (مع اختبارات الآن يمكن تقسيمه بأمان).
- **D4:** صور الملف الشخصي تُخزَّن base64 داخل قاعدة البيانات وتُرجَع في قوائم الموظفين؛ حجم الاستجابات يكبر. الأفضل ملفات + رابط.

- **D6:** `POST /api/quotations/:id/convert-to-invoice` بلا قفل: ضغطتان متزامنتان قد تنشئان فاتورتين. يحتاج transaction/تحديث ذري.
- **D7:** المراسلة: أي مستخدم مسجَّل يرى قائمة كل المستخدمين النشطين (الأسماء)، ولا حد لطول الرسالة.
- **D8:** مسارات إشعارات مكررة (`routes.ts` و`notification-routes.ts`)، و`console.log` منتشر بدل logger، والـ CSP فيه `'unsafe-inline'`، وإعداد الكوكي `secure/sameSite=none` ثابت (مصمَّم لـ Replit).

## استعلامات فحص مقترحة على قاعدة الإنتاج (قراءة فقط)

```sql
-- قيم فاسدة في الفواتير والدفعات والأرصدة (A1)
SELECT id, invoice_number, amount, paid_amount FROM invoices
 WHERE paid_amount::text = 'NaN' OR amount::text = 'NaN' OR paid_amount < 0 OR amount < 0;
SELECT id, invoice_id, amount FROM payments WHERE amount::text = 'NaN' OR (amount <= 0 AND COALESCE(is_refund,false) = false);
SELECT id, name, credit_balance FROM clients WHERE credit_balance::text = 'NaN' OR credit_balance < 0;
SELECT id, name, current_balance FROM payment_sources WHERE current_balance::text = 'NaN';

-- فواتير حالتها paid وبمبلغ مدفوع لا يساوي مجموع الدفعات (A3/A6)
SELECT i.id, i.invoice_number, i.status, i.amount, i.paid_amount, COALESCE(SUM(p.amount),0) AS payments_sum
  FROM invoices i LEFT JOIN payments p ON p.invoice_id = i.id
 GROUP BY i.id HAVING i.status = 'paid' AND i.paid_amount <> COALESCE(SUM(p.amount),0);

-- حسابات مستخدمين بدور Admin مكرر الاسم (C3)
SELECT name, COUNT(*) FROM roles GROUP BY name HAVING COUNT(*) > 1;
```
